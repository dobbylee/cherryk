# 검증과 하네스 발전

표준 실행과 리뷰 순서는 `AGENTS.md`에 있다. 이 문서는 변경에 맞는 검증을 고르거나
하네스 규칙을 추가·강화할 때 읽는다. 명령의 실제 구성은 `package.json`이 소유한다.

## 검증 선택

기본 테스트 게이트는 `pnpm test`이다. 전달 전에는 CI와 같은 `pnpm verify`를 실행한다.
`verify`의 loopback API origin은 빌드 산출물 검사에만 사용한다. 이를 호스팅하거나
호스팅된 통합 검증으로 보고하지 않는다. 실제 배포는 대상 환경의 origin을 사용한다.

| 변경            | 먼저 확인할 좁은 검증                        | 전체 게이트 외에 필요한 근거                                                |
| --------------- | -------------------------------------------- | --------------------------------------------------------------------------- |
| 화면·클라이언트 | 관련 Vitest, `pnpm test:frontend`            | 화면 동작이 바뀌면 데스크톱·모바일, 로딩·오류·인증 상태를 브라우저에서 확인 |
| API·Spring 모듈 | 관련 Gradle `--tests`와 TS 계약 테스트       | 공유 fixture, 호출 경로, 거부·실패 경로 보존                                |
| 스키마·영속성   | 해당 Testcontainers 마이그레이션/통합 테스트 | 빈 DB와 변경 전 데이터, 트랜잭션·동시성·데이터 보존                         |
| AI·OCR          | 공급자 fake/HTTP stub 및 출력 guard 테스트   | 실제 공급자 품질·비용 평가는 별도 작업으로 분리                             |
| 운영·CI·하네스  | `pnpm test:ops`, 변경 문서 포맷, diff 검사   | 이전 안전장치와 새 위치 대조, 변경된 실패 경로 재현                         |

Spring 단일 테스트는 `./backend/gradlew -p backend test --tests '<정확한 클래스>'
--rerun-tasks`로 실행한다. 포맷만 바뀐 문서에 문구를 그대로 복제하는 테스트는 추가하지
않는다. 버그 수정과 동작 보존 리팩터링에는 수정 전 실패·수정 후 성공을 보여 주는
좁은 검사를 추가한다.

## 테스트 환경과 안전성

- 통합 테스트 전에 `docker info`로 준비 상태를 확인한다. `pnpm test:backend`는 Docker
  확인 후 Gradle 테스트를 다시 실행한다. 연결·권한·이미지 pull 실패는 제품 실패와
  구분하며, skip·캐시 성공·임의 재시도로 통과 처리하지 않는다.
- DB 테스트는 기존 `PostgreSqlIntegrationTest.kt`의 격리된 Testcontainers 경계를,
  공급자 테스트는 기존 fake/stub 경계를 재사용한다. Production DB·실제 사용자
  데이터·운영 자격 증명을 테스트 입력으로 사용하지 않는다. `.env`를 통째로 출력하거나
  로그·리뷰·fixture에 비밀 값과 사용자 원문을 복사하지 않는다.
- 공유 DB·fake·환경 변수는 테스트별로 격리하거나 초기화한다. 시간·무작위 값은 기존
  Clock/random 주입 경계를 사용하고 고정 sleep 대신 관찰 가능한 완료 조건을 검사한다.
  같은 checkout의 Gradle 테스트, Next 빌드/개발 서버, 타입 생성을 동시에 실행하지 않는다.
- 실패 원인이나 변경된 입력 없이 전체 게이트를 반복하지 않는다. 통과한 단계도 새
  변경이 영향을 주면 다시 검증하며, 환경 복구 후에는 차단됐던 명령을 실제로 실행한다.
- 푸시가 승인되면 정확한 SHA의 `preview` CI 최종 성공을 확인한다. Production 전달과
  필요 시 전체 스택 Preview의 조건은 `decisions.md`를 따르며 운영 smoke는
  `backend/README.md`에 따라 수행한다.

## 판정 기준

구체적인 버그, 리뷰 누락, 수동 테스트 누락 또는 반복되는 혼란을 각 항목별로
0점부터 3점까지 평가한다.

- 심각도: 외형상 문제 `0`, 불편 `1`, 사용자에게 보이거나 반복 비용 발생 `2`, 보안,
  개인정보 보호, 데이터 손실 또는 신뢰 위험 `3`.
- 재발성: 일회성 `0`, 드묾 `1`, 반복되거나 인접 영역에서 발생 가능 `2`, 구조적 `3`.
- 탐지 가능성: 대체로 명확함 `0`, 리뷰에서 발견될 가능성이 높음 `1`, 놓치기 쉬움
  `2`, 런타임 또는 수동 테스트 전에는 보이지 않음 `3`.
- 규칙 적합성: 추측에 불과함 `0`, 문장형 알림 `1`, 범위가 좁은 체크리스트 `2`,
  저비용 실행 검사 `3`.

총점이 8점 이상이거나 심각도가 3점이면서 규칙 적합성이 2점 이상일 때만 하네스를
변경한다. 그 외에는 작업 메모만 남긴다.

## 최소 배치 위치

- 결정적이고 저비용인 항목: 테스트 또는 실행 가능한 검사.
- 판단이 필요한 항목: 리뷰어 프롬프트.
- 모든 작업에 필요한 항목: `AGENTS.md`.
- 절차 또는 평가 기준: 이 파일.
- 지속해서 적용할 프로젝트 선택: `agent-harness/decisions.md`.
- 현재 계획 또는 인수인계: `local/plan.md`가 안내하는 작업별 문서.

하네스를 변경할 때는 계기가 된 실패, 점수, 선택한 위치가 가장 작은 효과적 안전
장치인 이유를 기록한다. 중복 규칙을 추가하는 대신 기존 규칙을 강화한다.

## 기록된 안전장치

- `pnpm test`는 백엔드 테스트를 다시 실행하고 포맷을 검사하며, `pnpm verify`는 두
  애플리케이션을 빌드하고 Compose도 검증한다. 캐시된 Gradle 출력이 Docker로 인해
  차단된 통합 테스트를 숨기고 파일 7개가 저장소 포매터 형식에서 벗어난 뒤 이 규칙을
  추가했다(심각도 `2`, 재발성 `2`, 탐지 가능성 `2`, 규칙 적합성 `3`, 총점
  `9`). 패키지 스크립트가 가장 작은 결정적 검사이다.
- `local/plan.md`는 현재 상태만 담고, 지속해서 적용할 결정은 실행 가능하게 유지하며,
  완료된 롤아웃 증거는 작업 상세에 둔다. 완료된 마이그레이션 작업이 세 계층 모두에
  활성 지침처럼 중복해서 남은 뒤 기존 소유권 규칙을 강화했다(심각도 `2`, 재발성
  `2`, 탐지 가능성 `2`, 규칙 적합성 `2`, 총점 `8`).
- `preview` 브랜치는 CI 레인으로 유지하고 비Production Vercel 자동 배포는 비활성화하며,
  호스팅된 통합 환경의 위험이 있을 때만 완전히 격리된 Preview를 준비한다. 이 규칙은
  유지보수 오류를 반환해 인증이나 제품 흐름을 검증할 수 없었던 반복적인 읽기 전용
  Preview를 대체했다(심각도 `2`, 재발성 `2`, 탐지 가능성 `2`, 규칙 적합성 `2`,
  총점 `8`).
- 로컬 `verify`에는 필수 origin이 없고 CI에만 존재하여 환경에 따라 빌드 결과가 달랐다.
  두 진입점을 `pnpm verify`로 통일하고, 실행 순서·실패 전파·빌드에만 적용되는 origin을
  `ops/verification.test.mjs`로 검사한다(심각도 `2`, 재발성 `2`, 탐지 가능성 `2`,
  규칙 적합성 `3`, 총점 `9`). Docker 사전 확인은 위의 캐시/환경 실패 안전장치를 강화한다.
- 리뷰 설정과 프롬프트가 계획을 반복 로드하면서 `decisions.md`를 연결하지 않았고,
  변경 파일만 읽도록 제한해 수정되지 않은 계약과 안전 규칙을 빠뜨릴 수 있었다.
  규칙 소유권과 읽기 범위를 정리하고 원문 대조로 확인한다(심각도 `3`, 재발성 `2`,
  탐지 가능성 `2`, 규칙 적합성 `2`, 총점 `9`). 점검 근거와 이전/이후 검증은
  `local/plans/harness-refresh.md`에 기록한다.
